# Away

A web app to manage vacation requests.
- **Requesters** submit requests, follow their status, cancel pending requests, track their remaining vacation days and see the team vacations in a month calendar.
- **Validators** review all requests, filter them, then approve or reject them. They also manage the **work calendar**: weekly days off, holidays and events.
- Only **working days** count as vacation days. Weekly days off (Saturday and Sunday by default) and holidays are skipped.

## Setup

Requirements: Node.js 20+ and PostgreSQL 14+.

1. Create an empty database: `psql -U postgres -c "CREATE DATABASE vacation_db;"`
2. Copy `backend/.env.example` to `backend/.env` and set `DATABASE_URL` (your PostgreSQL user and password).
3. From the project root:
   ```
   npm run install:all   # installs root, backend and frontend packages
   npm run seed          # creates the tables (migration) and demo users (once)
   npm run dev           # API on :8888 and app on :5173
   ```
4. Open http://localhost:5173. API docs (generated by CEF) are at http://localhost:8888/doc.

To run the parts separately, use `npm run dev` inside `backend/` and `frontend/`.

To run the tests (PostgreSQL must be running): `cd backend`, then `npm test`. They cover the health check and the business rules.

Demo users (password `password123` for all): `alice@`, `bob@`, `carol@` and `david@example.com` (Requesters), `victor@` and `vera@example.com` (Validators).

```

  requests.http         API examples to try every route (VS Code "REST Client")
  src/
    index.ts            Entry point: finds the route, parses input, runs the handler, maps errors
    root.yaml           All routes, in OpenAPI format (CEF reads it)
    handlers/           Thin layer: check the role, call a service
    tests/              Health and business-rule tests (node:test), run with npm test
    services/           Business rules (vacationRules.ts), database access (vacationService.ts, calendarService.ts, authService.ts...). No HTTP code here
    migrations/         Database schema changes, run automatically at startup
    config.ts           Business numbers: yearly allowance, page sizes
    schemas/            Zod schemas that validate the input
    entities/           TypeORM tables: User, VacationRequest, WorkSettings, SpecialDay
    middleware/         JWT creation, cookie helpers and the authenticate() check
    events/             Events emitted by the service + listeners
    errors/             AppError and the error to JSON response
    db/                 Data source and seed script
    utils/              Date counting, pagination, JSON body parsing, login throttling
frontend/
  src/
    api/                Axios instance and one function per API call
    store/              Vuex modules: auth, requests, calendar, toasts
    router/             Routes and role guards
    views/              One file per page (login, my requests, dashboard, team, work calendar)
    components/         Reusable pieces (table, form, team calendar, badge, pagination, toasts...)
    utils/              Date helpers (month grid, working-day counting)
```

Request flow in the backend: `root.yaml` route -> input parser (Zod) -> handler -> service -> database.

## API

`POST /auth/login` puts the JWT in an `HttpOnly` cookie named `token`. The browser sends it back by itself on every request.

| Method and path | Role | Purpose |
|---|---|---|
| `POST /auth/login` | public | Log in, sets the JWT cookie, returns the user |
| `POST /auth/logout` | public | Log out, deletes the cookie |
| `GET /health` | public | Health check: API and database are up |
| `GET /me` | any | Current user |
| `POST /requests` | requester | Submit a request |
| `GET /requests/balance` | requester | My vacation days this year: allowance, used, remaining |
| `GET /requests?status&userId&page&limit` | any | Requests, paginated. A validator sees all and can filter by status and user. A requester only sees their own |
| `PUT /requests/:id/approve` | validator | Approve a request |
| `PUT /requests/:id/reject` | validator | Reject a request, body `{ "comment": "..." }` |
| `PUT /requests/:id/cancel` | requester | Cancel my own pending request |
| `GET /team/vacations?from&to` | any | Approved vacations that overlap the range (by default, those that have not ended) |
| `GET /users` | validator | Requesters, for the user filter |
| `GET /calendar` | any | Weekly days off and special days |
| `PUT /calendar/week` | validator | Set the weekly days off, body `{ "nonWorkingWeekdays": [6, 7] }` (ISO: 1 = Monday ... 7 = Sunday) |
| `POST /calendar/special-days` | validator | Add a holiday or event, body `{ "date", "name", "type": "HOLIDAY" or "EVENT" }`. It repeats every year |
| `DELETE /calendar/special-days/:id` | validator | Delete a special day |

Lists return `{ items, total, page, limit }`. Errors return `{ "error": "message" }` with a status code (400, 401, 403, 404, 409, 429). Every route has an example in `backend/requests.http` (VS Code "REST Client").

## Business rules

The pure rules are in `backend/src/services/vacationRules.ts`. The ones that need the database (overlap, allowance) are in `vacationService.ts`.

1. The end date cannot be before the start date. It may equal the start date, so one-day vacations are allowed (the specs say "after", which is unclear on this point).
2. A user cannot have overlapping requests (pending and approved requests count; rejected ones do not).
3. A request that is already approved, rejected or cancelled cannot be changed (409).
4. The start date cannot be in the past.
5. Rejecting needs a comment (checked in `requestSchemas.ts`).
6. Only validators can approve or reject (checked with `authenticate(event, Role.Validator)` in the handlers).

Bonus rules go beyond the specs:

7. **Yearly allowance.** Each user has 25 vacation days per year (`vacation_allowance` on the user). A request that needs more days than are left is refused (400). Pending and approved requests use up days. Rejected and cancelled ones do not. A request counts for the year of its start date.
8. **Cancel.** A requester can cancel their own pending request. Approved requests still cannot be changed.
9. **Working days.** A request uses only working days. Weekly days off and holidays are not counted, and a request with no working day is refused. The number is saved on the request (`days`), so later calendar changes do not alter it. Events are only shown on the calendar.
10. **Maximum range.** A request cannot cover more than 366 days.

## Technical decisions

- **CEF as the router.** Routes live in one file (`root.yaml`) and each one names its handler and its input parser. Handlers stay small.
- **Layers.** Handlers check the role and call a service. Services hold the rules and the database access. Entities describe the tables.
- **Validation with Zod** in one input parser per route. Bad input gives a 400.
- **One error type.** Code throws an `AppError` with a status. `index.ts` turns it into JSON.
- **Events.** The service emits `vacation.requested`, `.approved`, `.rejected` and `.cancelled`. A listener logs them. Email notifications could be new listeners.
- **JWT in an `HttpOnly` cookie.** JavaScript cannot read the cookie, so a script injected in the page cannot steal the token. The cookie is `SameSite=Strict` (protects against CSRF) and `Secure` in production. The browser sends it by itself, so the frontend has no token code. Only the user's public data is kept in `localStorage`.
- **Authorization in handlers.** CEF does not pass custom route keys, so handlers call `authenticate(event, role)`.
- **`PUT` for approve, reject and cancel.** CEF's CORS headers do not include `PATCH`.
- **Migrations, not `synchronize`.** The schema is changed by migration files in `src/migrations`, which run at startup. Generate a new one after changing an entity with `npm run migration:generate -- src/migrations/Name` in `backend/`.
- **Dates are `date` columns** sent as `YYYY-MM-DD`, so no time zone surprises.
- **Overlap check in SQL:** `start <= otherEnd AND end >= otherStart`.
- **Pagination in the database** with `skip`, `take` and a total count.
- **DTOs.** Entities are mapped to plain objects, so the password hash never leaks.
- **Transactions and row locks.** Creating a request locks the user's row, and approve, reject and cancel lock the request row. Two simultaneous calls are handled one after the other, so they cannot both pass the checks.
- **Login protection.** After 5 failed attempts an email is locked for 15 minutes (429). An unknown email takes the same time as a wrong password, so emails cannot be guessed.
- **Team calendar.** Each day shows the people on vacation as round initials, with a "+N" when there are many and a popup with all the names on hover. Non-working days are labelled.
- **Vuex** holds the session, request lists, work calendar and toasts. Display components get data through props.
- **Vite proxy** avoids CORS in development.

## Known limitations

- Seed-only users: there is no registration or password reset.
- The login lock is kept in memory, so it resets on restart and is not shared between several servers.
- A request cannot span two years (it is refused with a 400), because days are counted against the start year.
- The same holiday date applies to everybody (no per-country or per-user calendars), and holidays cannot differ by year.
- Events are in memory and only logged, so they are lost on restart.
- `npm audit` reports vulnerabilities in the backend dependencies of `commoneventframework` (`adm-zip`, `aws-sdk`) and in `ts-node-dev` (`esbuild`). There is no non-breaking fix.
